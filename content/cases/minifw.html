The firewall that blocked a 20 MB download for 24 hours

On the morning of a release deadline, a new lab test showed one of MiniFW-AI's oldest rules cutting a client off for 24 hours over an ordinary download. Earlier tests had passed only because the lab's virtual network cards hid the packets the rule counts. The fix was one condition, committed 57 minutes after the build it replaced, and the release shipped the same afternoon. No customer had installed the faulty build. I led the three-person team that built and shipped it.

Problem

MiniFW-AI is a behavioural firewall that runs on a site's existing Linux gateway. Its Financial edition, v2.2.13, had to isolate attacking clients on a financial customer's gateway, and isolate no ordinary staff, by the end of Friday 6 November 2026. A false isolation is expensive: a rule block cuts the client's forwarded traffic for 24 hours, and this release had no per-client exception for rule blocks.

The AI part of the plan had changed the day before. The packet model scores the first five packets of each TLS connection, which are the handshake. A guessed password travels later, encrypted, so the model could not see password guessing. We replaced it with a connection-rate model. It counts new TCP connections from one client to one server and port over 60 seconds, and isolates the client for 15 minutes at about 37 to 40 a minute.

So the release had two jobs: show that each isolation path fires on attacks, and that none fires on normal use. One acceptance check said a 20 MB download and a sustained stream must not be isolated. The failure turned up there.

The failure

In the release candidate, the packet-rate rule isolated two ordinary transfers for 24 hours, about 7 seconds after each started.

What the rule did

It isolates a client when any one of its flows measures more than 200 packets a second. On conntrack data, the rate is the counter change since the flow's first poll, divided by the time elapsed. At full-size packets, 200 a second is about 2.3 Mbit/s, so an ordinary download or stream crosses it. The rule dated from March 2026. It only became reachable on 2 November, when the engine began switching conntrack accounting on.

Why the tests missed it

Lab clients reach the gateway through virtual Ethernet pairs with segmentation offloads on (TSO and GSO). The kernel merges many segments into one large packet before conntrack counts it. With those defaults, no transfer passed 56 packets a second and nothing was isolated. An earlier check of downloads up to 300 MB passed for the same reason.

The test added on 6 November turned TSO, GSO and GRO off, so segments were MTU-sized, as on a network card that does not merge them first. Same transfers, same gateway:

Where else it fired

  • On the test gateway, the engine logged 218 packet-rate triggers in 55 minutes: 211 against its own loopback address during the dashboard's exports, and 7 against the test clients. After the fix it logged none, although several MB of evidence were copied off over SSH.
  • On a second lab gateway still running the older build, copying a file off with scp isolated the jump host for 24 hours. That was a real virtio network card, not a virtual pair.

The fix

The rule now runs only when a flow has real packet timing, which only the packet sensor provides. The burst, small-packet and timing rules already worked this way. On conntrack data the rule caught the wrong traffic: an ordinary download trips it, while a flood that opens a new connection per packet never builds one fast flow. The change is one condition and one unit test. Port-scan detection, deny lists, feeds, the other rules and the AI are unchanged.

The cost is coverage: a gateway without the packet sensor no longer has a per-flow packet-rate rule.

What changed afterwards

  • Lab bulk tests now run with offloads off. A pass with offloads on says nothing about a packet-rate rule.
  • The other edition gets the same fix before it ships.
